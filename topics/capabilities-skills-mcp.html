Capabilities and Sovereign Skills

The capability layer defines the operations an actor may perform and the conditions under which those operations are available. Sovereign Skills package these operations with contracts, knowledge, policies, evaluations, and provenance. Interfaces remain neutral to the reasoning model. A replaceable interoperability choice such as MCP can connect planners to capabilities, while institutional policy retains control over authorization, execution, and evidence.

Declared, permissioned operations

A capability describes an operation through its purpose, accepted inputs, expected outputs, affected resources, and applicable limits. Declaring these properties makes the operation inspectable before it is exposed to an agent or workflow.

Permission applies to a specific operation in context. Access to a tool does not imply permission to use every function, argument, dataset, or destination available behind it. The system exposes only the capabilities required for the authorized work and constrains their use.

Proposal, simulation, and execution have different effects and should remain distinguishable. A capability that previews a change does not automatically authorize the change itself. Consequential execution can require another policy check and human approval.

Sovereign Skill Packages

The proposed Sovereign Skill Package is a signed, portable capability package. Its contents can include a manifest, descriptive instructions, intent definitions, schemas, tools, workflows, knowledge, policies, evaluations, tests, a software bill of materials, and provenance.

The package declares what it does, which inputs and outputs it accepts, which models and tools it can use, which data classifications are permitted, how it is evaluated, and which approvals it requires.

These declarations make a skill more than instructional text. They provide a contract that a registry, policy authority, runtime, and evaluator can inspect. A signature and provenance record establish information about origin and integrity; evaluation and policy still determine whether the package is suitable for a particular use.

Domain skill packs can combine reusable primitives with domain-specific objects and rules. Institutional meaning remains in portable contracts and ontology references.

Interfaces independent of models

A planner should invoke capabilities through stable contracts rather than provider-specific assumptions. This separates the institution’s permitted operations from the model selected to reason about them.

A replacement model must understand the relevant contract and satisfy evaluation requirements. It does not receive broader permissions because it supports more tools or has a larger context window.

The same separation applies to workflow engines and user interfaces. A human-facing action and an agent-invoked action can refer to the same governed capability. Presenting an action in an interface does not create authority to execute it.

Replaceable interoperability under sovereign control

MCP is one replaceable reference choice for exposing capabilities across compatible components. Its interoperability role does not establish publisher trust, least privilege, supply-chain integrity, or institutional authorization.

A sovereign gateway around such an interface can enforce authentication, routing, classification, jurisdiction, secrets handling, provenance, and audit. External policy checks determine which operations become available for a particular intent and actor.

The proposed controls include deny-by-default access, constrained arguments, short-lived capability tokens, and a second gate for consequential actions. Capability sets can derive from SSIL intent and authorized work orders, keeping available operations connected to approved purpose.

Replacing the interoperability adapter should preserve the capability contracts, policy relationships, and evidence history.

Reference implementation

A generic build contains a capability registry, package records, a policy authority, an authenticated gateway, constrained execution workers, evaluators, and an evidence store.

The registry describes known publishers, schemas, and attestations. Supply-chain records connect packages to source, dependencies, licenses, build provenance, vulnerability findings, and approved environments. A lock manifest can identify the effective capability versions used for a particular run.

Workers receive only the necessary capabilities and credentials. Verification examines their outputs and declared behavior, while evidence records which package, authority, inputs, and execution context produced the result.
