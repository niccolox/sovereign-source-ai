Execution and Runtime

Execution turns an authorized work order into actions, artifacts, and recorded results. In Sovereign Source AI, agents and workers operate inside constrained environments whose permissions come from institutional policy. The runtime exists to enforce those boundaries, preserve evidence, and support independent operation. Its operating system, workflow engine, and infrastructure remain replaceable while intent, authority, requirements, and execution history remain durable.

The execution boundary

A Sovereign Work Order defines the authorized unit of work. It connects execution to a parent intent and specifies outputs, permitted capabilities, data access, dependencies, budgets, acceptance conditions, and required approvals. The platform selects an execution environment consistent with these constraints.

The agent cannot enlarge its own authority by choosing a different tool or requesting a more permissive environment. Child work orders inherit or narrow the authority of their parents. Their runs, actions, and artifacts remain connected to the original authorization.

Isolation makes this separation structural. Workers receive only the capabilities and credentials needed for their assigned work. Network access, secrets, storage, and dependency access are controlled outside the model. A worker produces candidate results and evidence; possession of a result does not confer authority to release it.

Agents, workers, and workflows

An agent interprets context and proposes or performs permitted actions. A worker supplies the bounded environment in which computation occurs. A workflow coordinates dependencies, durable state, approvals, and progress across multiple units of work.

These roles may share an implementation, but their responsibilities remain distinct. Workflow state should preserve what has completed, what remains pending, and which authority is required next. An interrupted model conversation should not become the only record of institutional work.

Release authority belongs outside disposable workers. The trusted release process evaluates candidates and their evidence before approving and signing an artifact. This prevents a compromised execution environment from also becoming the institution’s source of release authority.

Reference implementation

A generic reference build contains a policy gate, an execution scheduler, isolated workers, durable workflow state, artifact storage, and an evidence collector. The scheduler selects an approved runtime profile. Workers receive narrowly scoped credentials, perform authorized work, and return outputs with execution records. They are then destroyed or archived according to policy.

A FreeBSD-first runtime is one replaceable reference choice. Its role is to provide a controlled host environment with isolation, storage snapshots, and network restrictions. Other hardened runtimes can serve the same architectural role. Specialized compute can reside in a complementary environment when workload compatibility requires it.

Compute capability and isolation are separate decisions. A workload’s need for acceleration does not determine its permission to access institutional data, networks, or signing keys.

Restricted operation and runtime movement

Private or offline operation requires the critical execution path to remain usable within its permitted boundary. Models, packages, credentials, policy decisions, and evidence storage must be available through approved local resources where external connectivity is prohibited.

Moving a runtime means preserving more than executable files. Work orders, workflow state, dependency records, policy bindings, artifacts, and evidence must remain interpretable in the destination environment. Deployment definitions support this movement, but the decisive test is whether the institution can resume governed work without reconstructing its operating logic around a new provider.
